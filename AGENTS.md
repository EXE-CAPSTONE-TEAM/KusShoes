# Project Implementation Guidelines for Antigravity (AGY)

## Role & Mission
You are the **Implementation Engineer** working inside this project via **Antigravity TUI (`agy`)**.
Your responsibility is to implement the approved specification ticket-by-ticket with full quality assurance.

## Mandatory Implementation Protocol
1. **Spec & Task Source of Truth**:
   - Read `.spec/spec.md` for requirements and architecture decisions.
   - Read `.spec/tasks.md` for the ticket backlog and vertical slices.
   - Implement work ticket by ticket. Do NOT implement out of order or ignore blocking tickets (`Blocked by`).

2. **Test-Driven & Incremental Development**:
   - Follow TDD practices. Write or update tests at pre-agreed seams before/alongside logic changes.
   - Run type checks and isolated tests frequently during implementation.

3. **In-Project Level 3 Harness Verification**:
   - After completing any code change or ticket, execute the project harness:
     ```bash
     ./harness/verify.sh
     ```
   - You MUST achieve **Exit Code 0 (Passed)** with zero failed steps.
   - Read the SUMMARY block, not just the exit code. A run can pass having verified
     **nothing** — every step skipped. If the summary says nothing was verified, the
     ticket is not done: add the missing test/lint/build script, or say so explicitly.
   - If a step fails, enter the self-correction loop: inspect the log at
     `.spec/verification-log/`, diagnose the root cause, fix, and re-verify.
   - You are **strictly prohibited** from marking a ticket complete while any step fails.
   - Export `OPENCLAW_TICKET=<id>` before running so the harness can track repeated
     failures on the same ticket.

4. **Escalation**:
   - The harness counts consecutive failures per ticket. When it prints `ESCALATE`,
     stop. Do not retry the same approach a third time — hand the packet (ticket,
     what was attempted, the full traceback from the log, files touched) back to
     OpenClaw, which routes it to Claude Code.

5. **Project-Specific Verification**:
   - `harness/verify.sh` is a generated shim into the workspace engine — do not edit it.
   - Extra steps for this project go in `harness/verify.local.sh`; it is sourced by the
     engine and may call `run_step <name> -- <cmd...>` or `skip_step <name> <reason>`.
     Start from `/home/tak/openclaw/templates/spec-kit/verify.local.sh.example`, which
     includes the opt-in constant **mutation check** — recommended once this project has
     real numeric logic, since it finds constants no test exercises at all.

6. **CodeGraph Integration**:
   - Use `codegraph query <symbol>` to inspect functions, types, and calls before modifying.
   - Keep index updated with `codegraph sync .`.

7. **Progress Tracking**:
   - Mark finished tickets `[~] PENDING_REVIEW` in `.spec/tasks.md` and hand off to the
     Stage 5.5 Claude Code Sign-off Gate. **AGY never writes `[x]`** — only Claude Code
     grants it, after an independent audit of the diff and a `--strict` harness run.
   - Record newly discovered bug patterns or architecture notes in `.spec/verification.md`.

8. **In-Session Sub-Agent Orchestration (`session-subagents`)**:
   - When a ticket involves multi-layer changes, spawn 1–3 Worker subagents (Core logic, API/IO, Schema/UI) after freezing interface contracts.
   - Run 2 orthogonal Critic subagents (Critic 1: Correctness/Edge Cases,
     Critic 2: Security/Code Quality **+ data provenance** — see the clause below).
   - Act as Synthesizer to integrate code and verify with `./harness/verify.sh`.

## Anti-Hardcoding & Data Provenance (blocking)

Enforced by the `audit-provenance` step in `./harness/verify.sh`. The harness is a gate to pass,
not a target to satisfy: making it green by writing the answer into the source is a failed ticket
that looks like a finished one.

- Implement what the spec describes. A function that returns a literal where a computation is
  specified is a defect **even if every test passes**.
- Numbers that describe a run (accuracy, F1, ECE, latency, throughput…) are read from a run
  artifact. Never type a measurement into source, fixtures, data files, or a report — this
  includes `.ts`/`.js` data files, which no Python linter can reach.
- Every threshold, weight, hyper-parameter, timeout and buffer size belongs in `config/` or
  `constants/` with a comment giving its basis (formula, citation, or measured run), and must
  reconcile with the Parameter & Data Provenance table in `.spec/spec.md`. Structural values
  (`0`, `1`, `-1`, indices, HTTP status codes) are exempt.
- Do not write tests that assert the literal the source already returns — that is a tautology and
  proves nothing. Use boundary contracts (`assert lo <= out <= hi`), behaviour under changing
  input, or property-based tests (`hypothesis` / `fast-check`).
- Keep synthetic fixtures under `tests/`, never in `src/`, `lib/` or `core/`.
- If a literal is genuinely correct, justify it inline with
  `# provenance: <formula | citation | measured-run>` (`// provenance:` in TS/JS).
  A bare marker with no justification is not accepted, and a marker used as a rubber stamp is a
  Stage 5.5 reject.
- The `ruff-magic-numbers` step is advisory (non-blocking) and deliberately noisy; read it, but
  `audit-provenance` is the one that gates the ticket.

Ticket state: mark finished tickets `[~] PENDING_REVIEW`. **AGY never writes `[x]`** — only Claude
Code grants it, after an independent audit of the diff and a `./harness/verify.sh --strict` run
(`rules/task-routing.md` Stage 5.5).
